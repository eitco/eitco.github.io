1. Introduction

This guide explains how to use Arveo Flex Client and administer its scenarios, categories, dashboard presentation and translations. Start with User workflows for everyday tasks; Administration covers configuration and import/export for administrators.

2. User workflows

2.1. Access and permissions

Open Arveo Shell using the address supplied by your administrator and sign in with your own account. Open Flex Client from the Shell dashboard. The application runs inside Shell; a bookmark must use the Shell entry point. If authentication expires, sign in again through Shell. Before repeating a failed save, reload and check whether the change was already persisted.

A normal user works with scenarios made visible by configuration. Administrators additionally manage configuration and languages. Repository permissions still control access to data: a visible button or an enabled configuration switch does not grant permission. Ask your administrator when access is denied; do not repeatedly submit a destructive action.

2.2. Choose a scenario and language

Select English or Deutsch with the dashboard language selector. Scenario names, descriptions, category labels and field labels use the configured translations, falling back to the default text when a translation is missing. Open a scenario from a card or list row. Use the breadcrumb to return to the dashboard or to the parent record. Hidden scenarios are not available through ordinary navigation.

  • Categories: when category navigation is shown, choose a category to include its scenarios and those in all its child categories. All categories also includes unassigned scenarios; there is no separate Unassigned category in the dashboard. Your administrator can choose a flat catalog instead, hiding category navigation without removing scenarios or their assignments.

  • Search: search by scenario name or description in the current language. Search narrows the main catalog within the selected category, not repository documents. Clear the search and choose All categories when a scenario is unexpectedly missing. Results retain configured scenario order; use pagination to see more matches.

  • Favorites: use the favorite control to add or remove a personal shortcut. The favorites area shows your visible favorite scenarios independently of the main catalog’s search and category selection. A favorite does not grant repository access or make a hidden scenario visible.

  • Cards view / List view: choose how to display the catalog. This choice and your favorites are saved privately for your account. Search, selected category and page are temporary; they are not saved dashboard preferences. The administrator’s tree/flat choice is shared and is separate from your cards/list choice.

Scenario icons are chosen by the administrator. When no supported icon is configured, the dashboard shows the scenario’s initial instead.

If dashboard preferences cannot be restored, use Retry loading preferences. Changes remain pending until restoration succeeds, so they do not replace preferences that could not be loaded. If saving fails, use Retry saving dashboard preferences. A warning means the latest choices are not confirmed as saved; it does not prevent opening a scenario.

A one-stage scenario opens a document list. A two-stage scenario first opens a record list; selecting a record opens its documents. The selected record scopes child searches and creation. Confirm the parent before modifying documents.

2.3. Work in a Simple Document scenario

A Simple Document scenario opens one list directly. There is no parent-selection step. The list contains the permitted items of the configured type; its displayed title and fields are chosen by your administrator.

  1. Open the scenario card from the dashboard.

  2. Enter search values to narrow the list. Clear a filter to broaden the results again; use the offered sorting and column settings to arrange the list. More results load as you move through the list.

  3. Select an item to open its workspace alongside the list. Details shows metadata; Viewer is offered for document content; History appears when configured.

  4. Use the create action to add an item if it is available. Complete required writable fields and select/upload content as requested. Save and verify the new item in the list.

  5. Use an item’s edit or delete action where offered. Check the confirmation and persisted result. Closing the workspace returns attention to the list and does not delete the item.

Example: to inspect an invoice, search for its number, select the matching row, check Details, then open Viewer. If a filter hides the saved item, clear that filter before assuming the save failed.

2.4. Work in a Record scenario

A Record scenario first opens the record list. Selecting a record then opens a different list containing its related documents. Search and sorting apply to the stage currently on screen.

  1. Search for the parent record, for example a case number or folder name. Check identifying values before selecting it.

  2. Select the record to open its documents. Check the breadcrumb and configured parent summary to confirm the current context. An empty child list can mean that the record has no matching documents or that your search/access excludes them.

  3. Search within the selected record’s documents. Clearing the child search broadens results within that record; it does not turn the list into a search across all records.

  4. Select a document to open Details, Viewer and configured History, just as in a Simple Document scenario.

  5. To create a child document, first choose the correct parent and use the child list’s create action. The relationship to the current parent is controlled by the scenario; it is not an arbitrary editable grouping field.

  6. Close the document workspace when finished. Use the breadcrumb to return to the record list, then select a different record. Closing a document workspace alone does not change its parent context.

Parent record actions and child document actions are separate. Use the record list’s actions to create, edit, inspect history or delete a parent where offered. Use child actions for an individual document. Creating a record does not automatically create its documents. Changing parent metadata does not edit all children.

Before the deletion confirmation opens, the client counts the related documents. Check the count and whether those documents will be deleted or unlinked. If the count cannot be determined, the client reports an error and does not open the confirmation; retry after resolving the loading or access problem.

Warning
 Deleting a parent can delete all related documents when cascade deletion is enabled. Otherwise children are unlinked: their parent relationship is cleared, while their metadata and stored content are retained. They no longer appear under the deleted record. A mandatory relationship requires cascade deletion. Read the confirmation and ask your administrator when the affected scope is unclear.

2.5. Find and inspect documents

Use the search fields offered by the scenario, choose a supported operator and enter a value of the displayed type. For example, search for a known document name, then clear the search to return to the complete permitted list. Sort using the available table headings; use paging to move through results. Configuration determines available columns, order and searchable fields.

Select a row to open the document workspace. Choose Details to inspect metadata. Read-only fields cannot be changed. Dates, enumerations and references use their corresponding controls rather than arbitrary text. Not every configured field has a control in every view. There are no column-header filter controls or table CSV/ZIP export actions in this version.

2.6. Create, edit and delete

  1. Choose the create action when enabled. In a two-stage scenario, first choose the parent record.

  2. Complete all required writable fields. Select valid enumeration/reference values. Supply content when required by the chosen document type.

  3. Submit the form. Resolve validation errors next to their fields; preserve the draft until the outcome is clear.

  4. Confirm that the saved document appears in the correct list and reopen its details to check persisted values.

To edit, open the existing item and use its edit action. Change writable fields and save. Metadata-only edits leave unchanged content intact. When replacing original content, check filename and MIME information before saving. A failed save is not proof that nothing was stored: reload the item before retrying.

Deletion is permanent unless your repository provides a separate recovery mechanism. Read the confirmation carefully. Deleting a record can delete its children when cascade deletion is enabled; otherwise children are unlinked. Mandatory relationships require cascade behavior. Cancel if the affected scope is unclear.

2.7. Choose content and a viewer

Open Viewer in the document workspace. The client chooses the viewer from the selected content’s format, not from the scenario name. The same scenario can contain PDFs, images and text documents.

An original is a stored content element of the document. A rendition is another representation associated with an original, for example a PDF generated from another format. Renditions may be unavailable until repository processing finishes. They are not additional documents or historical versions.

When several configured elements are available, use the content selector above the viewer. Entries are grouped under their originals. The default element is chosen by the administrator and can be an original or a rendition. If only one element is available, there may be no selector. Check the selected entry before viewing or downloading.

There is no dedicated native Office, audio or video viewer in this client. A supported rendition may make such content viewable, for example a PDF rendition. HTML identified as text is shown as text rather than as an interactive webpage. Viewer display controls do not change stored content.

2.7.1. Read a PDF

  • Page navigation: use previous/next and the page-number control to move through the document. Check the displayed page count; document pages are distinct from pages of search results.

  • Magnification: use zoom controls or the offered fit modes to make text readable. A narrow workspace may hide toolbar items in an overflow menu; widen the workspace when needed.

  • Pan and selection: choose Pan to move around an enlarged page, or Selection to select text. These modes affect mouse interaction, not repository metadata.

  • Search: use the viewer’s search tool to find text inside this PDF. This is separate from scenario search. Image-only scans may contain no searchable/selectable text; the client does not perform OCR on demand.

  • Print: use the PDF print action when available. Browser printing and device selection occur outside the scenario configuration workflow.

  • Download: use the download action when enabled for the selected content. Check the filename and browser download destination.

2.7.2. View, edit and save PDF annotations

Annotations require enabled configuration and repository permissions. The viewer can show saved annotations without allowing you to edit them. Historical versions are read-only. Annotation settings belong to an original and also apply to its renditions.

  1. Use Show/Hide annotations to control their visibility. Hiding them is a display choice, not deletion. Editing tools are available only when annotations are visible and editable.

  2. Enter annotation editing through the toolbar. Text-markup tools include highlight, underline, strikethrough and squiggly underline. They require selectable text. Free-text and shape tools can be used for visible notes and markings.

  3. Select an annotation to change the offered fill/stroke color, thickness or opacity, move/resize it where supported, or delete it. Undo/redo operates on editing changes; it is not repository version restoration.

  4. Choose Save annotations to persist changes. Until saving succeeds, the draft is not proof of a stored annotation. Reopen the content to check the result when necessary.

  5. When changing content or leaving the document with unsaved annotation changes, use the offered Save and continue, Discard and continue, or Cancel choice. Cancel keeps the current document and draft open.

If annotations cannot load, use Retry and wait for a successful load before editing. A save failure requires resolving the error and retrying; do not discard a needed draft just to dismiss the message. Permission restrictions or loading errors can disable editing even while the PDF itself is visible.

2.7.3. Inspect an image

Use zoom in/out to change magnification and reset to return to the base zoom. Fit adapts the image to the available space; original-size display uses its natural dimensions. Rotate clockwise or counterclockwise to read sideways scans; these rotations affect the display only. Use fullscreen for more space and exit fullscreen to return to the workspace. Download obtains the selected stored content when enabled, rather than a screenshot of your rotated view.

The viewer component can navigate multiple supplied images, but this client supplies the selected content as one image. Use the document content selector to switch between stored originals/renditions; do not expect an image gallery of all documents. Image formats do not expose the PDF annotation toolbar.

2.7.4. Read a TIFF

TIFF files can contain several pages. Use previous/next or the page-number control to change the active page; toggle the thumbnail sidebar to identify pages visually. A single-page TIFF has no additional page to navigate to. Zoom in/out and reset adjust the active page’s display; rotation helps read sideways pages. Download, when enabled, retrieves the TIFF content, not merely the rendered page. PDF text search and annotation editing are not TIFF controls.

2.7.5. Read text content

Toggle line numbers when referring to a particular line. Enable wrapping to keep long lines within the viewer; disable it to preserve long-line layout and scroll horizontally. Text zoom changes displayed font size, and reset restores the base size. Copy text copies the content to the clipboard when the browser permits it; download saves the selected content when enabled. These actions do not edit the stored text. This viewer is a reader, not a source editor or a rendered HTML preview.

2.7.6. Downloads, unavailable content and historical viewing

Viewing and downloading are separate capabilities. Each original and rendition has its own availability and download settings; repository permissions still apply. A hidden download control does not mean the document has no content. An unsupported format offers a download fallback only when download is enabled.

Loading errors can result from inaccessible content, invalid format metadata, missing renditions or viewer initialization failures. Check the content selector, try an available original, and reload through Shell if needed. An empty preview alone does not establish an authorization failure. Report the scenario, document and selected element to your administrator without including credentials.

From History, open a historical version to inspect its content and version fields in a separate drawer. Historical content uses its own content selector. Close that drawer to return to the current version. Viewing an old version does not restore it; annotations of historical content cannot be edited.

2.8. Versions and comments

When history is enabled, open History. Select a historical version to inspect that version rather than the current document. Return to the current version before editing. Comments appear only where enabled and permitted; cancel an unfinished comment to discard it, or submit it and reopen history to check the saved result.

Historical selection is an inspection action; it does not restore or overwrite the current version. Record and document history are independently configured.

2.9. Recover from errors and unfinished work

  • Validation failure: correct the indicated fields and submit again.

  • List/loading failure: retry or reload through Shell; verify the selected scenario and parent record.

  • Permission denial: contact the administrator with the action and item involved, without sending credentials.

  • Session expiry: authenticate through Shell again, then check persisted state before repeating a write.

  • Navigation with unsaved work: save explicitly or intentionally discard your draft. Configuration and PDF annotation editing provide their documented save/discard/cancel choices. Do not assume that every other form draft has the same protection.

Recent records and saved views depend on scenario context and repository access. For removed or inaccessible records, return to the scenario and search again.

3. Administration

3.1. Enter administration

Sign in through Arveo Shell with a configuration-administrator account. Open Flex Client, then Open settings. Normal users cannot manage configuration. Repository access and configuration-administrator permissions are distinct; enabled scenario capabilities never override repository authorization.

Use the administration navigation to switch between Scenario configuration, Categories and Localization. Scenario settings, category hierarchy/assignments and dashboard presentation share one configuration draft. Moving between these workspaces retains unsaved changes; it does not save them. Enter through the Shell client and use this navigation rather than bookmarking a nested administration URL.

Select a scenario in the sidebar. The editor contains General, Content & Versions, and Views, with additional record sections for two-stage scenarios. Expand the relevant section. The JSON preview is read-only; edit using structured controls or validated import. Export a backup before significant changes.

3.2. Choose a scenario structure

A scenario is a configured entry point into repository data. Choose its structure before configuring its labels and views. The document and record types must already exist in the repository; this wizard does not create types or relationships.

The wizard identifies these choices as One-stage and Two-stage. This guide calls them Simple Document and Record scenarios. A record is the parent organizing the documents, not another content rendition.

3.2.1. Create a Simple Document scenario

  1. Step 1 - identity: choose One-stage and enter a unique scenario name. Use a stable descriptive identifier, for example invoice_documents. Leading and trailing whitespace is removed. The name must contain 1 to 200 characters; a duplicate name is rejected when creating the scenario. The name is its identity, while the displayed title can be configured later.

  2. Step 2 - document type: select the repository type containing the items you want to expose. For example, the demo uses flex_document. A type choice controls which attributes and content elements are available later. It does not convert existing objects to that type.

  3. Step 3 - defaults explanation: read the explanation of the proposed document configuration. This step is informational, not the attribute editor. The editor becomes available after creation.

  4. Step 4 - review: check the name, kind and document type. Choose Create only when these structural choices are correct. Successful creation immediately stores the scenario and opens its configuration; later changes require Save.

Next is disabled while a required choice is missing. Back returns to an earlier step; after changing a type, check the downstream choices again. Cancel closes the wizard without creating a scenario. A failed Create requires resolving the reported error; check the sidebar before repeating a request after a connection failure.

3.2.2. Create a Record scenario

  1. Step 1 - identity: choose Two-stage and enter a unique stable name, for example case_documents.

  2. Step 2 - architecture: select 1:n with foreign key (Strict one-to-many). This is the supported architecture: documents reference a parent record through a repository relationship.

  3. Step 3 - child document type: select an eligible document type. The choices are filtered to types with a supported child-to-parent relationship. In the demo, flex_rec_document is the child type. An empty list means that an eligible repository relationship is needed; choosing an unrelated type is not a workaround.

  4. Step 4 - relationship: choose the foreign key linking the child to its parent. Each option shows the relationship name, child attribute and target type/attribute. The target determines the record type; there is no separate arbitrary parent-type choice. A single eligible relationship is selected automatically. When there are several, choose the one that represents the intended grouping.

  5. Step 5 - review: verify name, kind, architecture, child type and relationship. For example, fk_flex_rec_document_container links the demo documents to flex_container. Create persists the initial scenario; configure its two stages next.

Going Back can clear dependent architecture, type or relationship selections. Recheck them before advancing. The wizard does not move documents, create parent records or repair repository relationships.

Important
 Name, kind, types and relationship structure are immutable after creation. To change the structure, create a new scenario. Duplicating also requires a new unique name.

3.3. Configure a Simple Document scenario

Select the new scenario in the sidebar and work through its document settings. Start with a small set of useful fields, save, then test it as a normal user before making it visible to the wider audience.

  1. Set the displayed title, description and dashboard visibility. A useful title such as Invoice documents is easier to recognize than a technical type name. Hiding a scenario removes ordinary navigation; it does not revoke repository access.

  2. Expand the document’s General settings. Enable globally available attributes and give them clear labels. Review mandatory, primary-key, read-only and unique badges before enabling creation or editing.

  3. Configure table/search persistence and the exposed create/edit capabilities. Persistence controls remembered view state; it does not store repository documents. Repository permissions still decide whether an action is allowed.

  4. Configure Content and document Versions as described below. Choose a default available content element and decide which originals and renditions users can view or download.

  5. Configure Document views: the table for finding items, search fields for narrowing results, detail/form fields for inspecting and editing them, and version fields where history is enabled.

  6. Save and reload. Open the scenario as a user, search for a known item, inspect its metadata and content, and check that the enabled actions and required fields are usable.

Example: for invoices, expose invoice number and date in the list, add corresponding search fields, and organize writable metadata in a meaningful form section. Keep repository-maintained fields read-only. Enable download only for the content elements users need.

3.4. Configure a Record scenario

A Record scenario has two independently configured stages. Record is stage 1, the parent list; Document is stage 2, the documents of the selected record. The configuration editor may display Document settings before Record settings; these labels determine the target, not their screen order.

  1. Review the immutable child type and relationship. Confirm that the derived parent type represents the intended record, such as a case or folder.

  2. Configure Record General attributes and actions. Include fields that help identify the parent, such as its name or reference number. Parent create/edit settings do not enable child creation or editing.

  3. Configure Record views separately: record table columns and search fields identify the parent, detail fields describe it, and summary fields display context after selection. Set summary order, labels and highlighting where offered. Include enough information to distinguish similarly named records.

  4. Configure Document General and Document views for the child type. Use child attributes, not parent attributes, in these matrices. Child searches are scoped by the selected relationship and record.

  5. Configure document originals, renditions and annotation behavior. Parent records without content do not gain a document viewer merely because document content is enabled.

  6. Enable Record versions/comments and Document versions/comments independently. Choose version fields appropriate to each type.

  7. Review Record management before exposing deletion. With cascade enabled, deleting a record deletes its child documents first. With cascade disabled, the client unlinks children before deleting the parent. A mandatory parent relationship cannot be cleared and forces cascade behavior; do not attempt to disable that safeguard.

  8. Save and test both stages: find a record, open its child list, check the summary, inspect a child and return to the parent list. Repeat with another record to verify that documents are scoped correctly.

Example: put case number and case title in the Record table and summary, and document name and document date in Document views. A case title label does not rename a child document field. Explain deletion policy to users before allowing parent deletion.

3.5. General settings and attributes

Set the localized title, description and dashboard visibility. Visibility controls navigation, not security. Each document or record stage has its own creation and editing switches. Disable these actions when they should not be exposed; repository authorization still applies. Deletion availability also depends on permissions, and Record management determines the treatment of children.

Choose a scenario icon from the icon picker in General settings. The icon is used in dashboard cards, favorites and list rows. Choose the default option to restore the scenario initial. Imported icon identifiers that are valid but unavailable in this client are retained and also display the initial; do not supply SVG markup or an image URL as an icon identifier.

The attribute matrix displays type information and mandatory, primary-key, read-only and unique metadata. These badges describe the repository contract. Enable available fields and preserve required writable fields when creation or editing is enabled. Do not try to make a repository read-only attribute editable.

Localized text includes a default value and optional values per language. Use the localization drawer to supply translations. A field/view label override applies only where enabled; otherwise the normal configured label applies. Preview each supported language after saving.

3.6. Content, versions and record deletion

Expand Content & Versions. Configure original and rendition labels, availability and independent download switches. Choose an available default content element or rendition. Annotation settings belong to the original and are shared by its renditions; default visibility must be disabled when annotations are disabled.

Optional filename and MIME attributes must reference writable string fields. If omitted, repository content metadata supplies the values. The primary upload populates configured filename/MIME fields; other content elements retain their own metadata. Editing the filename before submission also changes the primary content’s system name.

Enable version history and comments separately for document and record stages. These options control the client surfaces, not underlying permission grants.

For two-stage scenarios, review record-management cascade deletion. With cascade enabled, deleting a parent deletes its documents first. Without it, the parent relationship is cleared on the children; their metadata and stored content are retained. A mandatory parent relationship forces cascade deletion. The deletion confirmation shows the related-document count and the configured delete or unlink consequence. If the count cannot be loaded, confirmation is blocked. Test the configured policy with a disposable record and explain this consequence to users before exposing record deletion.

3.7. Configure views

Expand Views and select the document or record view. Configure globally available attributes first, then their supported use in search, table, detail and create/edit views. Adjust order and labels with the provided controls. Only actual runtime consumers are customer features: a configuration field alone does not establish an available UI action.

  • Search: enable fields and arrange their order. Runtime controls and operators follow each field type; the matrix does not offer an arbitrary operator editor.

  • Table: configure available columns, ordering and visibility and sorting. Verify the result in the runtime list.

  • Detail/forms: configure field ordering, sections and read-only behavior where supported; required writable fields must remain accessible for enabled mutations.

  • Two-stage summary: configure parent summary fields and localized labels, then verify the selected-record context.

3.7.1. Understand the view matrices

Setting Meaning and practical use

Global attribute Available

Makes an attribute eligible for configured views. Enable it here before using it in a view. Turning it off can remove dependent uses; inspect the editor’s confirmation and validation.

View Available

Includes the field in this particular table, search, detail, version or summary view. It does not grant repository permission.

Order

Moves a field to the requested position in that view. Orders in another stage or matrix remain independent.

Label override

Uses a view-specific label when enabled. Otherwise the stage attribute label is used. Supply translations through the provided translation action.

Table Visible

Controls initial visibility among available columns. Users may have remembered column choices when persistence is enabled.

Table Sortable

Allows sorting by the column where supported by the repository/runtime. Enable it for useful sortable fields, not every displayed value automatically.

Detail Section

Groups fields under a localized section heading, for example General or Classification.

Detail Read-only

Prevents editing that field through the configured form. It cannot make a repository read-only attribute writable.

Version fields

Determines which configured metadata fields are shown for history. Enabling history and selecting its fields are separate choices.

Summary fields

Displays parent context for Record scenarios, with order, labels and highlighting where offered. It does not change child attributes.

Do not hide required writable inputs from enabled creation/editing workflows. Primary keys, system-maintained fields and the relationship managed by a Record scenario may be locked. A field can be visible in a table and absent from search, or searchable and absent from the table; these are independent choices.

Column-header filtering and CSV/ZIP table export are not available in this version. Do not configure a workflow around those actions.

3.8. Organize scenarios into categories

Open Categories. Categories organize dashboard navigation; they do not create repository folders, move documents or grant permissions. Each category has a stable ID and a required default label, with optional translations. Renaming or translating a label does not change the ID or its assignments.

  1. Enter a nonblank label and choose Add root category. To create a nested category, select its parent and choose Add child category.

  2. Select a category to edit its default label or translations. Do not leave the required default label empty or whitespace-only.

  3. Use the parent selector to move a category and its children under another category, or back to the root. A category cannot become its own ancestor. Moving to another parent appends it to that parent’s children.

  4. Use Move up and Move down to order categories among siblings. Category order controls navigation order, not the order of scenarios in the catalog.

  5. Under Scenario assignments, choose one category for each scenario or leave it Unassigned. Hidden scenarios can also be assigned. A parent dashboard filter includes scenarios assigned to its descendants; unassigned scenarios appear under All categories only.

  6. Choose Save all to persist the shared configuration draft, including any retained scenario or dashboard-presentation edits. Verify the saved dashboard as a normal user.

Deleting a category requires confirmation and removes its entire subtree from the draft. Scenarios assigned anywhere in that subtree become unassigned; the scenarios and repository data are not deleted. Save all to persist the removal. Back up the full configuration when assignments must be recoverable; a category-only export does not contain them.

3.8.1. Choose shared dashboard presentation

In Categories, choose the tree/category presentation or the flat catalog and then Save all. Tree presentation shows category navigation. Flat presentation shows all visible scenarios in configured order without a category filter. Both retain search, favorites, cards/list selection and pagination.

This is an administrator-owned setting for everyone, not a private user preference. Switching to flat retains the category tree, translations and scenario assignments; switching back to tree restores their navigation structure. It also preserves users' favorites and cards/list preferences.

3.8.2. Import and export categories only

Export categories downloads categories.json: a JSON array containing the current draft’s complete category tree, including unsaved edits, stable IDs, translated labels and child order. It contains no scenarios, category assignments, scenario icons or dashboard presentation. For example:

[
  {
    "id": "finance",
    "label": { "default": "Finance", "values": { "de": "Finanzen" } },
    "children": [
      { "id": "invoices", "label": { "default": "Invoices" } }
    ]
  }
]

  1. Choose Import categories in Categories and select a category-array file, not a full configuration envelope.

  2. Review validation errors before retrying. IDs must be globally unique and labels valid. New roots and children are appended in imported order. An existing ID must retain the same label/translations, parent and sibling position; a conflicting definition aborts the whole import. Use the editor, not import, to rename or move an existing category.

  3. After successful validation, review the merged draft and choose Save all. Import does not immediately persist anything and does not change scenario assignments or dashboard presentation.

An empty or identical category import makes no changes; it does not delete existing categories. Invalid files, conflicting definitions or failed validation leave the draft unchanged. If the draft changes while validation is running, repeat the import against the current draft rather than assuming the earlier result was applied.

3.9. Save, duplicate, order, import and export

3.9.1. Save and discard scopes

Save editor changes and verify the result after reloading. The scenario editor’s Save current saves the selected scenario. When category or dashboard-presentation changes are pending, the action becomes Save all and saves the complete shared configuration draft, even when the selected scenario itself is unchanged. Revert current discards only the selected scenario’s edits; it does not undo category, presentation or other scenario edits.

Save all in Categories also persists retained scenario edits. Confirmed configuration reload discards the whole shared configuration draft and restores saved data, rather than only the visible workspace. Export needed drafts before discarding them.

Leaving administration with unsaved configuration or localization changes opens Unsaved administration changes. Choose Save, Discard or Cancel deliberately. A failed save retains the unfinished draft. While a save is in progress, wait for it to finish before navigating or starting another write. The browser’s close/reload warning is not a save action.

Duplicate a scenario when you need a similar configuration with a new identity. Change order using the sidebar ordering controls and save where requested. Export one scenario or the full configuration through the provided action. Store the export securely; it may contain business-specific labels and configuration.

3.9.2. Configuration transfer and legacy files

Configuration exports use a version-2 envelope with schemaVersion, categories, scenarios and scenarioPresentation. A single-scenario export uses the same envelope, including the full category tree and presentation but only the selected scenario. It is not a bare scenario object or a category-only array. Full configuration export is the appropriate backup for scenarios, their assignments and the shared dashboard layout; neither export includes private dashboard preferences.

To import configuration, use the JSON import action in Scenario configuration. Imports merge by scenario name, keeping unrelated scenarios and categories. Matching names update compatible scenario settings; they do not permit changing immutable structure or conflicting category assignments. Category conflicts abort the import. The complete merged draft must pass schema and live repository validation before it is applied. Review it and save explicitly; import success is not a successful save.

An explicit scenarioPresentation in a v2 import selects tree or flat. If it is omitted from a v2 import, the current draft choice is retained. This merge behavior differs from a new v2 configuration, where omission defaults to tree.

Legacy files containing only { "scenarios": […​] } or { "schemaVersion": 1, "scenarios": […​] } are also accepted by this import action. They are converted to v2 with flat presentation before validation, without repairing scenario fields. Existing unrelated scenarios and categories remain; an existing scenario’s conflicting category assignment still prevents import. Unknown fields/versions and mixed legacy/v2 envelopes are rejected. An empty scenario array does not clear the existing configuration. Subsequent exports always use v2.

Delete only the intended scenario after reviewing confirmation. Configuration removal does not itself describe a repository data-deletion workflow. Reset replaces configuration with seeded defaults; back up first and use reset only in an explicitly disposable or otherwise authorized environment.

3.10. Manage languages and translations

Open localization administration from the settings navigation. Choose a catalog language, search by translation key or text, edit the translation and save. Enable a language for users only when it is suitable for your audience. Select the language on the dashboard and check both static UI text and scenario labels.

Missing text uses the default language. Scenario-owned labels and global UI translations are separate. An unsaved translated draft is not persisted by changing the runtime language. Translation generation, when offered, needs a configured available provider; review generated text before accepting overrides. This guide does not assume that a generation provider is installed.

Category labels belong to the shared configuration, not the global UI catalog. In Localization, edit the required raw default label separately from explicit translations for each language. Changing the catalog’s default language does not move or overwrite a category’s stored translation. Empty or whitespace-only category defaults block saving and must be corrected at the field. Label edits do not change IDs, hierarchy or scenario assignments.

Localization saves only resources with pending edits. If the shared configuration and catalog both have changes, configuration is saved first, followed by the catalog. A partial-success message means configuration was saved but catalog changes remain unsaved; correct the error and retry the remaining work. Saving configuration may include scenario, category or presentation edits retained from the other administration workspaces.

Reload is unavailable during a save. When shared configuration edits exist, its confirmation covers both localization and configuration: confirming discards retained scenario, category and presentation edits as well as localization changes. Cancel to keep those drafts.

3.11. Validation and concurrent editing

Invalid references, duplicate scenario names or category IDs, blank category defaults, dangling category assignments, unavailable default content, inconsistent annotation switches, missing required fields and unsupported relationships prevent a save. Correct the indicated setting rather than removing validation.

A stale save is rejected when another administrator has changed the scenario or shared configuration being saved. Your draft is retained. Preserve a copy of the intended edits, explicitly reload the saved configuration and reapply necessary changes. Remember that a shared reload can discard edits from other administration workspaces. This version does not provide a conflict-specific merge interface. For authorization or session errors, sign in again through Shell and check current state before repeating writes.
