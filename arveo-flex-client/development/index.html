1. Introduction

This guide explains how to use Arveo Flex Client and administer its scenarios, categories, dashboard presentation and translations. Start with User workflows for everyday tasks; Administration covers configuration and import/export for administrators.

2. User workflows

2.1. Access and permissions

Open Arveo Shell using the address supplied by your administrator and sign in with your own account. Open Flex Client from the Shell dashboard. The application runs inside Shell; a bookmark must use the Shell entry point. If authentication expires, sign in again through Shell. Before repeating a failed save, reload and check whether the change was already persisted.

A normal user sees only visible scenarios with an explicit scenario-access grant. Direct links require the same grant. Access alone does not permit reading records, documents or content: actions have independent grants and must also be enabled in configuration. Administrators can configure all scenarios but receive no automatic scenario grants. Repository authorization still applies independently. Ask your administrator when access is denied; do not repeatedly submit an action.

Columns, details and create/update fields may have independent visibility and editability rules. Hidden fields do not appear; visible restricted fields are read-only. A form cannot submit if a required restricted field cannot be satisfied. Navigation refreshes permissions. If permissions change, protected views disappear and further unauthorized submissions are blocked; unsaved input is retained only in memory. An ECR denial preserves input and does not remove the Flex grant.

2.2. Choose a scenario and language

Select English or Deutsch with the dashboard language selector. Scenario names, descriptions, category labels and field labels use the configured translations, falling back to the default text when a translation is missing. Open a scenario from a card or list row. Use the breadcrumb to return to the dashboard or to the parent record. Hidden scenarios are not available through ordinary navigation.

Use the dashboard search and card/list view controls to find scenarios, and mark favorites for quick access. When your administrator uses tree presentation, choose a category in the sidebar to narrow navigation. Flat presentation does not use that category hierarchy. Optional scenario icons and categories help navigation; neither changes document membership or grants repository access.

  • Categories: when category navigation is shown, choose a category to include its scenarios and those in all its child categories. All categories also includes unassigned scenarios; there is no separate Unassigned category in the dashboard. Your administrator can choose a flat catalog instead, hiding category navigation without removing scenarios or their assignments.

  • Search: search by scenario name or description in the current language. Search narrows the main catalog within the selected category, not repository documents. Clear the search and choose All categories when a scenario is unexpectedly missing. Results retain configured scenario order; use pagination to see more matches.

  • Favorites: use the favorite control to add or remove a personal shortcut. The favorites area shows your visible favorite scenarios independently of the main catalog’s search and category selection. A favorite does not grant repository access or make a hidden scenario visible.

  • Cards view / List view: choose how to display the catalog. This choice and your favorites are saved privately for your account. Search, selected category and page are temporary; they are not saved dashboard preferences. The administrator’s tree/flat choice is shared and is separate from your cards/list choice.

Scenario icons are chosen by the administrator. When no supported icon is configured, the dashboard shows the scenario’s initial instead.

If dashboard preferences cannot be restored, use Retry loading preferences. Changes remain pending until restoration succeeds, so they do not replace preferences that could not be loaded. If saving fails, use Retry saving dashboard preferences. A warning means the latest choices are not confirmed as saved; it does not prevent opening a scenario.

A one-stage scenario opens a document list. A two-stage scenario first opens a record list; selecting a record opens its documents. The selected record scopes child searches and creation. Confirm the parent before modifying documents.

2.3. Work in a Simple Document scenario

A Simple Document scenario opens one list directly. There is no parent-selection step. The list contains the permitted items of the configured type; its displayed title and fields are chosen by your administrator.

  1. Open the scenario card from the dashboard.

  2. Enter search values to narrow the list. Clear a filter to broaden the results again; use the offered sorting and column settings to arrange the list. More results load as you move through the list.

  3. Select an item to open its workspace alongside the list. Details shows metadata; Viewer is offered for document content; History appears when configured.

  4. Use the create action to add an item if it is available. Complete required writable fields and select/upload content as requested. Save and verify the new item in the list.

  5. Use an item’s edit or delete action where offered. Check the confirmation and persisted result. Closing the workspace returns attention to the list and does not delete the item.

Example: to inspect an invoice, search for its number, select the matching row, check Details, then open Viewer. If a filter hides the saved item, clear that filter before assuming the save failed.

The sidebar shows Documents in a Simple Document scenario. When your administrator enables Recycle Bin and grants access, Recycle Bin opens trashed documents directly. Record scenarios also provide Records and nested Records/Documents destinations in Recycle Bin. Breadcrumbs above the workspace show the scenario and current destination and let you return to an ancestor. Table headings distinguish Documents, Records, Trashed Documents and Trashed Records; these labels follow the selected language. When a search includes trashed items, a muted row tint and a narrow status column identify them. The header reserves the same space as each row, so business values stay aligned whether an item is active or trashed.

2.4. Work in a Record scenario

A Record scenario first opens the record list. Selecting a record then opens a different list containing its related documents. Search and sorting apply to the stage currently on screen.

In an m:n scenario, the same document can appear under several records with the same identity. The selected record’s document filters, counts and pages are evaluated within its membership; the separate flat document view is not evidence that a document belongs to a particular record. Records without links display an empty list. See Share documents between records (m:n) for sharing, creation and removal instructions. Sharing does not copy the document.

  1. Search for the parent record, for example a case number or folder name. Check identifying values before selecting it.

  2. Select the record to open its documents. Check the breadcrumb and configured parent summary to confirm the current context. An empty child list can mean that the record has no matching documents or that your search/access excludes them.

  3. Search within the selected record’s documents. Clearing the child search broadens results within that record; it does not turn the list into a search across all records.

  4. Select a document to open Details, Viewer and configured History, just as in a Simple Document scenario.

  5. To create a child document, first choose the correct parent and use the child list’s create action. The relationship to the current parent is controlled by the scenario; it is not an arbitrary editable grouping field.

  6. Close the document workspace when finished. Use the breadcrumb to return to the record list, then select a different record. Closing a document workspace alone does not change its parent context.

Record labels show only currently permitted metadata, falling back to the record ID. Recent-record history uses record IDs so saved descriptive labels cannot reveal fields that are now hidden.

Parent record actions and child document actions are separate. The record summary card’s three-dot menu offers Edit, Delete and Trash for active records, or Restore and permanent Delete for trashed records, according to scenario settings and permissions. It uses the same confirmation workflows as the record list. Use the record list’s actions to create, edit, inspect history or delete a parent where offered. Use child actions for an individual document. Creating a record does not automatically create its documents. Changing parent metadata does not edit all children.

For a 1:n with foreign key scenario, before the deletion confirmation opens, the client counts the related documents using record-scoped document read permission. Cascade deletion requires record-scoped document delete permission; unlinking requires record-scoped document edit permission and permission to update the relationship field. All-document workspace grants do not substitute for these permissions. Check the count and whether those documents will be deleted or unlinked. If the count cannot be determined, the client reports an error and does not open the confirmation; retry after resolving the loading or access problem. Record deletion is blocked for m:n scenarios, regardless of the cascade setting.

Warning
 In a one-to-many scenario, deleting a parent can delete all related documents when cascade deletion is enabled. Otherwise children are unlinked: their parent relationship is cleared, while their metadata and stored content are retained. They no longer appear under the deleted record. A mandatory foreign-key relationship requires cascade deletion. Read the confirmation and ask your administrator when the affected scope is unclear.

2.4.1. Share documents between records (m:n)

An m:n membership associates an existing document with a record. It is not a copy or a move. Editing shared metadata or content changes the same document wherever it is linked.

  1. Open the document from a selected record’s document list or the scenario’s flat document view.

  2. Open Details, then Edit document. The picker requires enabled document editing and the document-edit permission for the active workspace. Record-scoped grants and all-document grants are independent.

  3. Search in Add document to record and check the identifying values of the target record. The picker searches authorized records using administrator-configured fields, independently of authored table columns and personal column preferences; record-read and field visibility permissions still restrict those values. An empty result is not proof that a record does not exist or is accessible to you.

  4. Choose one record. Already-linked records are marked and cannot be selected again. Selection is staged: searching, choosing, clearing an unsaved choice or closing the drawer does not add or remove a membership.

  5. Choose Save. Verify the document in the target record’s list and in its previous record’s list. Existing memberships are preserved; repeating a confirmed addition does not create another membership. A membership-only save does not create a document version.

Example: a document under case A can also be added to case B without copying its content. An edit from either case is visible from the other. Adding it to B does not remove it from A.

To create a document, first open the intended record’s document list and use its create action. The new document is initially linked to that record. Creation requires the configured creation setting and both document-create and document-edit permissions, but can remain enabled when editing existing documents is disabled. Retrying a failed initial link without further metadata changes also works in this create-only configuration. Adding an additional record requires enabled document editing. Creation is disabled in the m:n flat document view because no current record is selected. Repository authorization still controls every write.

To remove a membership:

  1. Open the record whose membership you intend to remove and confirm the breadcrumb.

  2. Use the document row’s Remove from this record action, which requires document-edit permission independently of the document editing switch.

  3. Check the confirmation. Cancel changes nothing; confirm removes only this record-document membership.

  4. Check the refreshed list. The document and its other record memberships are preserved. Removing its final membership leaves it unassigned rather than deleting it.

Important
 Delete document everywhere is a separate disabled action. Record deletion is also blocked in m:n scenarios with cascade both ON and OFF. A verified repository-wide relationship cleanup contract is required before these workflows can be enabled. Do not reset data or apply one-to-many deletion instructions to bypass this safeguard.

If a membership read fails, use the editor’s Retry action and wait for a successful load before adding a record; the pending choice is preserved. A failed search also preserves your choice. A partial-save error keeps the drawer open: completed document changes and the confirmed identity remain saved, while the pending addition is retained for retry. If creation succeeded but its initial link failed, retry completes the link using the same identity. If creation could not be confirmed, check the repository before creating again. A failed or uncertain removal is not reported as success; check the refreshed membership before retrying.

2.5. Find and inspect documents

Use the search fields offered by the scenario, choose a supported operator and enter a value of the displayed type. For example, search for a known document name, then clear the search to return to the complete permitted list. Sort using the available table headings; use paging to move through results. Configuration determines available columns, order and searchable fields.

When a field uses an administrator-configured lookup, select a permitted repository value from its dropdown instead of entering arbitrary text. Labels can combine several columns with ` — `; the filter uses the stored key, never the displayed label. Depending on its settings, the dropdown allows one or several selections and optional case-insensitive search. Multiple stored keys match with OR within that field; other active fields still narrow the query. When search is enabled, start typing and continue in the same input as the dropdown opens; opening it does not move focus to Retry. Typing searches the options without applying a document filter until a value is selected. Empty lookup search filters show the field name inside the input, matching the other search fields, rather than as a separate label above it. Multiple-selection dropdowns show checkboxes beside the matches and stay open when a value is selected or deselected. Click a row or use the arrow keys and Enter to toggle a value; press Escape or click outside to close the dropdown. While a selected key is being validated, the dropdown stays open and further checkbox changes are temporarily unavailable; continue selecting once validation finishes. Checkboxes reflect confirmed selections only. Changing visible matches preserves selections on other pages. Scroll through the matches to browse more records. Single- and multiple-selection dropdowns automatically load the next page when you reach the final 10% of the scroll range, without a Load more records button. If loading fails, use Retry to continue. Active lookup filters show the latest selected match in that input without extra search captions, repeated labels or selection-removal buttons. The green filter chips use the same configured display columns as the dropdown, including for restored selections; unresolved values fall back to their stored key. Use a chip’s × button to remove only that selected key: other selections and active fields remain applied, and the dropdown reflects the remaining selections. Removing the last key clears that lookup filter; Clear all removes all filters. Filtering still uses exact stored keys, not chip labels, even when several selections have the same label.

Select lookup values individually, including across pages; lookup-filter Select all is deferred to AFC-134 and is not available. Press Escape to close the dropdown and cancel its search. The search text clears, and reopening starts with unfiltered values. Committed selections and active filter chips remain. Replace the input text to start another query, or erase it to browse unfiltered values; editing the search text alone does not remove active filter chips.

Restored lookup selections resolve separately from dropdown search and paging. A value outside the visible page is not cleared. Unavailable or ambiguous saved selections and retry actions remain visible beside the lookup input when the dropdown is closed; the stored keys remain in the active chips. If the administrator changes a mapping or disables its filter, incompatible saved filter preferences are discarded before querying. If its source type disappears or is no longer a supported document/container type, the lookup control is omitted until the configuration can be repaired.

Lookup browsing and saved-value resolution also require access to a configured source scenario and permission to read its records or documents. All configured label, stored-value and dropdown search columns must be visible in that source’s Details and permitted for you. If access changes or a required column is hidden, the lookup cannot use another scenario to bypass that restriction in the matching active source. Keep existing selections and ask an administrator to check the source scenario and field visibility; an unavailable lookup is not proof that a saved value was deleted.

Select a row to open the document workspace. Choose Details to inspect metadata. Read-only fields cannot be changed and retain their stored values when other fields are saved. Dates, enumerations and references use their corresponding controls rather than arbitrary text. Not every configured field has a control in every view. There are no column-header filter controls or table CSV/ZIP export actions in this version.

2.6. Create, edit and delete

  1. Choose the create action when enabled. In a two-stage scenario, first choose the parent record.

  2. Complete all required writable fields. Select valid enumeration/reference values. Supply content when required by the chosen document type.

  3. Submit the form. Resolve validation errors next to their fields; preserve the draft until the outcome is clear.

  4. Confirm that the saved document appears in the correct list and reopen its details to check persisted values.

To edit, open the existing item and use its edit action. Change writable fields and save. Metadata-only edits leave unchanged content intact. When replacing original content, check filename and MIME information before saving. A failed save is not proof that nothing was stored: reload the item before retrying.

Configured metadata lookups show a single-selection dropdown. Choose the displayed item; its stored key, not its label, is saved. A saved value outside the current page or dropdown search is resolved independently. Optional editable fields offer Clear selection; required fields still need a value, and read-only or permission-restricted fields cannot be changed through the dropdown.

Wait while selections load. Empty results do not mean that an existing value should be erased. If loading fails, keep the draft and use Retry. A confirmed unavailable selection remains visible: depending on the administrator’s policy, it is preserved or an editable field requires replacement before saving. An ambiguous/invalid selection is not resolved by choosing the first matching row. A temporary service failure is shown separately and does not silently clear data or turn into a removal.

In a strict one-to-many scenario, an administrator may enable choosing another parent. Creation starts with the selected record’s referenced key, which need not be its ID. If the parent field is editable and you have the required grant, select another parent and save. After a successful move, the original record’s document list refreshes and the moved document disappears from that list. Creation under another parent likewise does not add a row to the original parent’s list. A failed save retains your draft parent selection for retry; it does not change the persisted relationship. When the setting is disabled or the field is read-only, keep the existing parent. Many-to-many scenarios continue using their separate membership controls.

Trash and permanent deletion are different actions. Where the scenario enables the recycle bin, use Trash to retain an item for restoration. Selected documents can be trashed or restored together. For a record action, confirmation shows related items and, when configured, asks whether to include children. Restoring included children restores all trashed children, even those trashed earlier. Restoring a single document may first require restoring its parent; declining that parent restoration cancels the document action. Native repository cascades are automatic.

Permanent deletion still requires its own confirmation and cannot be undone. For the existing active-record deletion workflow, one-to-many cascade deletion removes children; disabling it unlinks children, and mandatory foreign keys require cascade behavior. In m:n scenarios, use Remove from this record for membership removal. The recycle-bin feature remains in development; see the administration chapter’s development notice before relying on it. Cancel if scope is unclear.

Deleting an active record follows the same cascade/unlink policy with Recycle Bin on or off. The count includes all linked documents. If any child is trashed, restore it before choosing an unlink policy. Deleting children permanently needs the corresponding active-delete or trash-purge permissions. Individual document deletion from a record also works with Recycle Bin on or off and remains limited to that record. If an item changes between active and trashed during permanent deletion, execution stops; refresh and confirm the current state before trying again.

Permanently deleting a trashed record always deletes its trashed children first; active linked children must be moved to the recycle bin beforehand. Restore, Delete and Trash are separate actions. Restoring a parent through a native cascade can restore other trashed siblings too, including documents trashed independently. Read the total impact before confirming.

For bin deletion, enter the displayed name exactly, or DELETE for bulk/unnamed items. Restore needs no deletion phrase. Cancelling makes no changes. A failed or interrupted action may have completed some steps: refresh the list and inspect the items before starting again. Repository retention restrictions still apply.

2.7. Choose content and a viewer

Open Viewer in the document workspace. The client chooses the viewer from the selected content’s format, not from the scenario name. The same scenario can contain PDFs, images and text documents.

An original is a stored content element of the document. A rendition is another representation associated with an original, for example a PDF generated from another format. Renditions may be unavailable until repository processing finishes. They are not additional documents or historical versions.

When several configured elements are available, use the content selector above the viewer. Entries are grouped under their originals. The default element is chosen by the administrator and can be an original or a rendition. If only one element is available, there may be no selector. Check the selected entry before viewing or downloading.

There is no dedicated native Office, audio or video viewer in this client. A supported rendition may make such content viewable, for example a PDF rendition. HTML identified as text is shown as text rather than as an interactive webpage. Viewer display controls do not change stored content.

2.7.1. Read a PDF

  • Page navigation: use previous/next and the page-number control to move through the document. Check the displayed page count; document pages are distinct from pages of search results.

  • Magnification: use zoom controls or the offered fit modes to make text readable. A narrow workspace may hide toolbar items in an overflow menu; widen the workspace when needed.

  • Pan and selection: choose Pan to move around an enlarged page, or Selection to select text. These modes affect mouse interaction, not repository metadata.

  • Search: use the viewer’s search tool to find text inside this PDF. This is separate from scenario search. Image-only scans may contain no searchable/selectable text; the client does not perform OCR on demand.

  • Print: use the PDF print action when available. Browser printing and device selection occur outside the scenario configuration workflow.

  • Download: use the download action when enabled for the selected content. Check the filename and browser download destination.

2.7.2. View, edit and save PDF annotations

Annotations require enabled configuration and repository permissions. The viewer can show saved annotations without allowing you to edit them. Historical versions are read-only. Annotation settings belong to an original and also apply to its renditions.

  1. Use Show/Hide annotations to control their visibility. Hiding them is a display choice, not deletion. Editing tools are available only when annotations are visible and editable.

  2. Enter annotation editing through the toolbar. Text-markup tools include highlight, underline, strikethrough and squiggly underline. They require selectable text. Free-text and shape tools can be used for visible notes and markings.

  3. Select an annotation to change the offered fill/stroke color, thickness or opacity, move/resize it where supported, or delete it. Undo/redo operates on editing changes; it is not repository version restoration.

  4. Choose Save annotations to persist changes. Until saving succeeds, the draft is not proof of a stored annotation. Reopen the content to check the result when necessary.

  5. When changing content or leaving the document with unsaved annotation changes, use the offered Save and continue, Discard and continue, or Cancel choice. Cancel keeps the current document and draft open.

If annotations cannot load, use Retry and wait for a successful load before editing. A save failure requires resolving the error and retrying; do not discard a needed draft just to dismiss the message. Permission restrictions or loading errors can disable editing even while the PDF itself is visible.

2.7.3. Inspect an image

Use zoom in/out to change magnification and reset to return to the base zoom. Fit adapts the image to the available space; original-size display uses its natural dimensions. Rotate clockwise or counterclockwise to read sideways scans; these rotations affect the display only. Use fullscreen for more space and exit fullscreen to return to the workspace. Download obtains the selected stored content when enabled, rather than a screenshot of your rotated view.

The viewer component can navigate multiple supplied images, but this client supplies the selected content as one image. Use the document content selector to switch between stored originals/renditions; do not expect an image gallery of all documents. Image formats do not expose the PDF annotation toolbar.

2.7.4. Read a TIFF

TIFF files can contain several pages. Use previous/next or the page-number control to change the active page; toggle the thumbnail sidebar to identify pages visually. A single-page TIFF has no additional page to navigate to. Zoom in/out and reset adjust the active page’s display; rotation helps read sideways pages. Download, when enabled, retrieves the TIFF content, not merely the rendered page. PDF text search and annotation editing are not TIFF controls.

2.7.5. Read text content

Toggle line numbers when referring to a particular line. Enable wrapping to keep long lines within the viewer; disable it to preserve long-line layout and scroll horizontally. Text zoom changes displayed font size, and reset restores the base size. Copy text copies the content to the clipboard when the browser permits it; download saves the selected content when enabled. These actions do not edit the stored text. This viewer is a reader, not a source editor or a rendered HTML preview.

2.7.6. Downloads, unavailable content and historical viewing

Viewing and downloading are separate capabilities. Each original and rendition has its own availability and download settings; repository permissions still apply. A hidden download control does not mean the document has no content. An unsupported format offers a download fallback only when download is enabled.

Loading errors can result from inaccessible content, invalid format metadata, missing renditions or viewer initialization failures. Check the content selector, try an available original, and reload through Shell if needed. An empty preview alone does not establish an authorization failure. Report the scenario, document and selected element to your administrator without including credentials.

Content and annotations may be unavailable while a document is in the recycle bin, including content and annotations of historical versions. Retention does not guarantee preview or download access while trashed; a failed read does not prove that content was deleted. If access is needed, use the authorized Restore workflow, review its related-item impact before confirming, then reopen the content after restoration. Ask your administrator if restoration is unavailable. See Recycle-bin configuration (in development) for the current limitation.

From History, open a historical version to inspect its content and version fields in a separate drawer. Historical content uses its own content selector. Close that drawer to return to the current version. Viewing an old version does not restore it; annotations of historical content cannot be edited.

2.8. Versions and comments

When history is enabled, open History. Select a historical version to inspect that version rather than the current document. Return to the current version before editing. Comments appear only where enabled and permitted; cancel an unfinished comment to discard it, or submit it and reopen history to check the saved result.

Historical selection is an inspection action; it does not restore or overwrite the current version. Record and document history are independently configured.

2.9. Recover from errors and unfinished work

  • Validation failure: correct the indicated fields and submit again.

  • List/loading failure: retry or reload through Shell; verify the selected scenario and parent record.

  • Permission denial: contact the administrator with the action and item involved, without sending credentials.

  • Session expiry: authenticate through Shell again, then check persisted state before repeating a write.

  • Navigation with unsaved work: save explicitly or intentionally discard your draft. Configuration and PDF annotation editing provide their documented save/discard/cancel choices. Do not assume that every other form draft has the same protection.

Recent records and saved views depend on scenario context and repository access. For removed or inaccessible records, return to the scenario and search again.

When a configuration administrator has no accessible visible scenarios, the dashboard explains that scenario access requires an explicit mapping and offers a configuration shortcut. Administration remains available. Your administrator can browse the permission catalog and configure access; no permissions are granted automatically.

2.10. Document workspace settings

In Record scenarios, Documents lists all scenario documents and a selected record lists only its linked documents. Administrators can configure these workspaces independently, so their columns, filters, details and permitted actions may differ. Each workspace remembers its own enabled table and search preferences. Content and version capabilities share the scenario’s document-type settings.

3. Administration

3.1. Enter administration

Sign in through Arveo Shell with a configuration-administrator account. Open Flex Client, then Open settings. Normal users cannot manage configuration. Repository access and configuration-administrator permissions are distinct; enabled scenario capabilities never override repository authorization.

Use the administration navigation to switch between Scenario configuration, Permission catalog, Categories and Localization. Scenario settings, category hierarchy/assignments and dashboard presentation share one configuration draft. Moving between these workspaces retains unsaved changes; it does not save them. Enter through the Shell client and use this navigation rather than bookmarking a nested administration URL.

Each administration page starts with a short explanation. Configuration cards describe their purpose and provide a direct action. Shared type settings distinguish global attribute availability from view-specific visibility; permission pages distinguish configuration defaults from individual rules. Expand How are these rules applied? for the rule explanation. The global Permission catalog shows discovery status separately from identity search and usage inspection.

Choose Scenario Configuration in the navigation to open the scenario list. Search by scenario name, title or type, filter by stage kind, or use Create, Import and Export all. Select a scenario to open its overview, which shows its description, identity, structure, types and visibility, plus Export, Duplicate and Delete. Use the Configuration and Permissions navigation cards or sidebar children to open the corresponding editor. The breadcrumb shows Dashboard, Scenario Configuration, the scenario title and the current section; ancestor links navigate back. Clicking the Scenario Configuration row opens the list and toggles its submenu. Clicking a scenario row opens its overview and toggles its children, closing other scenario branches. The chevron is part of the row. Clicking anywhere on a scenario card opens its overview. Cancelling an unsaved-change prompt preserves the current page and menu expansion. The Configuration sidebar contains General and View Configuration. Each grouping opens a landing page with links to its children. General contains Overview (naming, icon, dashboard and record management) and TypeDefinitions (record and document attributes, versions and content). One-stage scenarios omit record settings. View Configuration follows runtime navigation: Records contains Record search and Documents within a record; Documents configures direct document search. Select a screen area using its button or the example image to open its settings without deeper navigation. Breadcrumb ancestors return to their landing pages. The JSON preview is read-only; edit using structured controls or validated import. Export a backup before significant changes. Unsaved edits are retained between a scenario’s overview, Configuration and Permissions pages. Moving to another scenario or the scenario list asks you to save, revert or cancel when the current scenario is dirty. 3.4. Configure a Record scenario

A Record scenario has shared record/document type settings and three independently configured runtime workspaces: Record Search View, Record Documents View, and Documents (all documents). View Configuration groups the record workspaces on the Records page and the all-document workspace on the Documents page. Documents inside a selected record can have different table columns, search filters, detail fields, action permissions and saved preferences from all documents.

  1. Review the immutable child type and relationship. Confirm that the derived parent type represents the intended record, such as a case or folder.

  2. Open General → TypeDefinitions and use the Record sections to configure shared record attributes and history. Include fields that help identify the parent, such as its name or reference number. Parent create/edit settings do not enable child creation or editing.

  3. Under View Configuration → Records, expand the Record search sections and configure record table columns, search filters and details. On that same Records page, configure the Record summary card and expand the Documents in record sections for child-document table, search and details. Configure View Configuration → Documents separately from the Documents in record sections on Records. Both use child attributes; only Record Documents View is scoped by the selected relationship and record.

3.7.2. Configure lookup-backed attributes

Open General → TypeDefinitions and expand Attribute lookups inside the Document or Record card. Select an attribute and enable a shared lookup mapping. Lookup sections expand like Attributes, Content and Versions; they are not separate nested cards. The header lists attributes with enabled mappings as Active lookup filters, or shows No lookup filters set up when none exist. This summary remains visible when collapsed and updates with draft edits; it does not depend on dropdown search being enabled. Disabled mappings and imported filter/form settings without a shared mapping are not listed as active. The source must be an accessible repository document or container type represented by a configured scenario of the same type and object kind. A container source needs the record stage of a Record scenario; a document source needs a document stage. Users need access to that source scenario and permission to read its records or documents; configuring a lookup does not grant these permissions.

Make every configured display, stored-value and dropdown search column visible in the source stage’s Details and permitted for the user. This includes id when explicitly chosen for any of those purposes; retaining an item’s identity internally does not make id an unrestricted lookup column. The active scenario is preferred when it is an eligible source; otherwise sources follow configuration order. If a matching active source hides a required column, the lookup does not switch to another scenario to bypass the restriction. Missing source access or hidden required columns make the lookup unavailable rather than exposing restricted fields. Check this setup with the intended normal-user permissions, not only as an administrator.

For a Record scenario, the document lookup source, stored column and labels are shared by the all-document and record-scoped document workspaces. Their filter and form dropdown settings are independent. Open the record view configuration and select its document workspace to edit those scoped settings; changing them does not change the all-document dropdowns. Saving validates all configured workspaces, including retained settings on a workspace you are not currently editing.

When reopening the editor or switching scenarios, the attribute selector initially shows the first attribute with a saved lookup, if one exists. Select another attribute to inspect or configure its settings; an ordinary attribute correctly shows lookup disabled. An explicit attribute choice remains selected while editing the current stage.

  1. Choose the source type and a unique stored-value column compatible with the target attribute’s scalar type. For example, store a unique customer code while displaying the customer’s name and city. A composite unique key is not sufficient for a single stored column.

  2. Select and order the display columns. Their formatted values are joined with ` — `; users see this label, but queries and saves use only the stored value.

  3. Choose what happens when a saved value is no longer available: Preserve keeps it, while Require replacement requires a valid selection before an editable form can save. A temporary lookup failure is not proof that the value was removed.

  4. Configure filter and form dropdown search independently. Enable search and select columns with Equals, Contains or Starts with. Only display columns have an Order control; search-column order does not affect matches or result sorting. Text matches are case-insensitive and matches across columns combine with OR. Non-text scalar columns support Equals only. A query that cannot represent a column’s type skips that column, so a name search can still match text columns alongside numeric Equals columns. If no column can accept the query, no matches are returned. Disabling search leaves browsing available.

  5. For the filter, choose single or multiple selection. Users select individual values and can retain selections across dropdown pages. Forms always select one value.

  6. Save the scenario, reload it, and verify the permitted workflow as a normal user. Full version-2 exports retain the mapping and both sets of dropdown settings; existing configurations without these optional fields remain valid.

Each dropdown search attribute may appear only once, even with a different operator. Imported column objects can pass JSON Schema’s whole-object uniqueness check yet fail semantic validation for repeating an attribute; remove the duplicate before saving. Lookup-filter Select all is not available; it is deferred to AFC-134. Imports reject the retired selectAllEnabled property even when it is false; remove only that property from older branch-created exports. Before deploying this unreleased contract update, an administrator must also clean any saved configuration containing it, otherwise startup validation fails. There is no automatic cleanup or data reset; preserve other settings and saved filter selections.

Changing a source does not silently rewrite the stored, display or search columns. Removed, inaccessible or incompatible references remain in the draft with validation errors so that you can repair them explicitly. A mapping on a foreign-key field must match the repository’s declared relationship; an ordinary lookup does not create a relationship.

Imported filter/form lookup settings without a shared attribute mapping remain marked for repair. Enabling the shared mapping preserves those authored surface settings; complete the source and column mapping before saving. Scenario, category and localization configuration saves all apply the same lookup and parent-selection validation, so stale settings must be repaired even when the current edit is elsewhere.

For a strict one-to-many foreign-key scenario, the optional recordManagement.parentSelectionEnabled setting is disabled by default. The configuration editor does not offer an Allow choosing another parent record toggle; existing or validated imported settings remain supported. When enabled in the stored configuration, users can choose another parent during document creation or editing. The picker derives its source and stored column from the selected relation; a non-ID referenced key is supported. Existing create/edit grants and relation-field read-only rules still apply. This setting does not alter many-to-many membership workflows or introduce new permissions.

Parent selection uses the dropdown search settings and relation-field read-only rule of the current document workspace. A read-only relation in the record-scoped form remains locked even when the all-document form allows reassignment, and conversely.

3.9.2. Configuration transfer and legacy files

Configuration exports use a version-2 envelope with schemaVersion, categories, scenarios and scenarioPresentation. Full configuration export is the appropriate backup for scenarios, their assignments and the shared dashboard layout; neither export includes private dashboard preferences.

To import configuration, use the JSON import action in Scenario configuration. Imports merge by scenario name, keeping unrelated scenarios and categories. The complete merged draft must pass schema and live repository validation before it is applied. Review it and save explicitly; import success is not a successful save.

Legacy files containing only { "scenarios": […​] } or { "schemaVersion": 1, "scenarios": […​] } are also accepted by this import action. They are converted to v2 with flat presentation before validation, upgrading document-view structure while preserving authored settings. The backend upgrades valid stored V1 configuration on startup rather than requiring a reset. A merge retains the current dashboard presentation when the imported V2 file omits that setting.

Category labels belong to the shared configuration, not the global UI catalog. In Localization, edit the required raw default label separately from explicit translations for each language. Changing the catalog’s default language does not move or overwrite a category’s stored translation. Empty or whitespace-only category defaults block saving and must be corrected at the field. Label edits do not change IDs, hierarchy or scenario assignments.

Localization saves only resources with pending edits. If the shared configuration and catalog both have changes, configuration is saved first, followed by the catalog. A partial-success message means configuration was saved but catalog changes remain unsaved; correct the error and retry the remaining work. Saving configuration may include scenario, category or presentation edits retained from the other administration workspaces.

Reload is unavailable during a save. When shared configuration edits exist, its confirmation covers both localization and configuration: confirming discards retained scenario, category and presentation edits as well as localization changes. Cancel to keep those drafts.

3.12. Validation and concurrent editing

Invalid references, duplicate scenario names or category IDs, blank category defaults, dangling category assignments, unavailable default content, inconsistent annotation switches, missing required fields and unsupported relationships prevent a save. Correct the indicated setting rather than removing validation.

A stale save is rejected when another administrator has changed the scenario or shared configuration being saved. Your draft is retained. Preserve a copy of the intended edits, explicitly reload the saved configuration and reapply necessary changes. Remember that a shared reload can discard edits from other administration workspaces. This version does not provide a conflict-specific merge interface. For authorization or session errors, sign in again through Shell and check current state before repeating writes.

3.14. Configure scenario permissions

Select a scenario and use the Configuration and Permissions navigation destinations. Both edit the same scenario draft. Permission drawers stage their changes separately until you choose Save; the page Save/Save all then persists the scenario draft. The Permissions overview groups scenario access, actions and field controls. Search by feature, attribute or criterion; filter explicit rules, configuration defaults, entries without grants or disabled targets. Grouped tables show Name, Allowed and Denied with the complete configured identity labels and a three-dot menu at the end of each row. Empty sections are hidden. These lists describe configuration, not a user’s effective access.

Edit permissions only in the scenario’s Permissions section. Configuration feature switches and view matrices contain no permission controls. Each permission row’s three-dot menu contains only Edit Permission, which opens the shared right-hand drawer. Browse one catalog, initially filtered to All, and select an identity; its dialog offers green Allow, red Deny, and Cancel. The wide drawer keeps the Allow and Deny lists prominent above the catalog, with a Remove button for every entry in either list. Any allow criterion may grant; any matching deny wins. Client roles retain their client identity, groups retain full paths, and claim values retain their type. Disabled features retain editable rules.

Configure the scenario-wide Configuration defaults rule above the permission tables. Edit its Allowed and Denied criteria using the same staged drawer. Configuration status is read-only text in the table. Choose No grants, Configuration defaults, or Explicit permission rule inside the editor. Rows using defaults show their resolved criteria, labelled as inherited, and follow changes to the shared rule. No grants always denies. Explicit rules remain independent. New scenarios start with every row using defaults and a shared Allowed criterion for realm role flex-admin, with no Denied criteria. Administrators can edit this initial rule; existing scenarios retain their saved settings. Previously omitted field rules show Existing configuration behavior; explicitly choose Configuration defaults to opt them into the shared rule. Without a default rule, inherited actions grant nothing and inherited fields retain their configuration behavior. An explicitly empty default rule denies.

For fields, table visibility, detail visibility, create visibility/editability and update visibility/editability are independent. Rules can only restrict existing schema/configuration availability and writability. Removing the final criterion from an explicit rule leaves an empty denying rule.

At the bottom of Permissions, Reset to factory defaults asks for confirmation, restores the shared Allowed criterion for realm role flex-admin, clears Denied criteria and all explicit row rules, and sets every row to Configuration defaults. Other scenario settings are preserved. Reset remains an unsaved draft change until page Save/Save all.

Select multiple rows across sections to add identities to all selected Allowed or Denied lists. Section selection affects only its visible rows; selected rows remain selected when filtering. Clear the selection explicitly or switch scenarios. Bulk additions merge into existing rules without duplicates or removals. Save in the drawer applies additions to the scenario draft; Cancel discards them.

Choose Validate Permissions for advisory checks of the current draft. Hints identify missing catalog identities, duplicates, identities present in both lists, obsolete field references, unavailable grants and missing access/viewing prerequisites. For example, annotation grants cannot enable content whose availability is disabled. Findings refresh after draft changes and link to the affected configuration. Checks do not simulate user memberships, block saving or automatically change rules.

A stale catalog warning retains existing selections. Deployment operators provision read-only discovery credentials and register selectable audiences and typed claim values. Administrators do not select criteria based only on their own identity. Imports reject unsupported new criteria, including deny rules; correct the complete mapping before saving.

Schema v2 exports include the scenario’s action rules and field overrides, with no discovery credentials, cached catalogs or current-user grants. Supported v2, v2 and v2 imports upgrade without generating grants. Existing scenarios without mappings deny access after migration: configure initial access and action mappings before rollout. Configuration administration does not automatically grant business access.

3.15. Browse the permission catalog

Open Permission catalog in administration navigation to browse all discovered realm roles, client roles and groups, independently of your own memberships. Search by role, client identifier or full group path and filter by category. Audiences and custom claims are registered by operators and are marked separately from Keycloak entries.

The page shows the last successful discovery and warns when its snapshot is stale. Reload catalog reloads the server snapshot; discovery retries occur at most every five minutes. If discovery has never succeeded, ask your operator to configure the dedicated read-only Keycloak discovery account. Existing choices and scenario mappings survive an outage. The inventory itself remains read-only. Each entry shows its number of configured occurrences, including unsaved changes and hidden scenarios. Identities referenced by scenarios but absent from the catalog are also shown as Missing from catalog. Absence from an unavailable or stale snapshot is unconfirmed.

Sort the catalogue by Source, Identity, Usage count or Status using the column headers. Open Usage details from an entry’s trailing three-dot menu to see each scenario, action or field/control and its Allowed/Denied disposition. Remove an individual occurrence to update the shared administration draft. Removing the final identity preserves the explicit empty rule; it does not restore field inheritance. Choose Save to persist the shared draft, or Discard changes to discard all unsaved administration changes, including changes made on other configuration pages. Navigation to a usage retains the draft. Validate Permissions checks all scenarios on this page.

To grant or deny access, open the scenario’s Permissions page and select catalog entries in the target’s drawer. Configure SCENARIO_ACCESS and the required action rules, then save the scenario. Configuration administration alone grants no scenario access. You can use administration even when the dashboard shows no scenarios. Navigation to the catalog retains unsaved configuration drafts.

The drawer header and Save/Cancel footer stay visible while the body scrolls. Save applies only its working copy to the scenario draft. Cancel, Escape and drawer dismissal discard drawer-only changes. Canceling the identity-choice dialog leaves the drawer draft intact. Save the scenario page to persist applied edits.

Select a permission name to open Affected UI. Choose a location to see its effect and, where useful, a highlighted screenshot. Use Zoom in for a larger, readable image. One rule can apply to several locations; changing the selected location does not create or edit a rule. Edit Permission opens the existing editor. The preview is independent of bulk-selection checkboxes and remains open when filtering the list. On smaller screens it appears above the tables. Close preview closes only the explanation.

The screenshots are static English examples. They do not show your exact configured fields, unsaved changes or a user’s effective access. Each field is identified by its actual target label; the image highlights a representative region. Read the conditions for related permissions and configuration requirements. Historical content shares content-view/download rules, while historical annotations cannot be edited. Unimplemented actions and effects without a useful screenshot are explained in text.

Select the Configuration defaults heading to inspect targets explicitly using the shared rule. An omitted field rule retains existing configuration behavior and is not an explicit defaults selection.

The Permissions tables contain independent targets for table visibility, detail visibility, create visibility/editability and update visibility/editability. Select targets across sections and choose bulk Allow or Deny to collect additions in the drawer. Save merges criteria, skips duplicates and retains unrelated controls. Bulk operations add only; remove existing criteria or return to defaults by editing an individual permission.

The scenario permission overview shows Configuration status. Search applies together with the selected filter. Configuration defaults includes explicit defaults selections and field controls retaining inherited configuration behavior; the visual defaults explanation lists only explicit consumers of the shared rule. Explicit empty rules deny access.

Choose Use configuration defaults inside a permission editor to stage an explicit selection of the shared scenario rule. Save applies that choice to the scenario draft; Cancel retains the previous rule. Visibility and editability remain independent. An omitted field rule retains existing configuration behavior, while an omitted action grants nothing.

The catalogue also discovers explicitly configured access-token audiences and hardcoded string, boolean or number claims from Keycloak clients and client scopes. Operator-registered criteria remain available. Dynamic claim mappers do not provide selectable values, and an empty group category can mean the realm has no groups. The catalogue does not show user memberships or automatically grant permissions.

The permission catalog scrolls continuously without pagination. Permission Identity precedes Source. Click a column heading to sort; the arrow shows its direction. Row three-dot menus open usage details.

3.15.1. Independent document permissions and upgrades

The Permissions editor lists Documents and Record Documents View separately, including content, download, annotation and history actions. A grant in one workspace does not grant the corresponding action in the other. Shared content and version feature switches remain under General and still limit availability in both. The record summary card has its own field-visibility permissions.

Current exports use schema version 2. Supported older imports and stored configurations copy their existing document view settings and permission selections into both document workspaces, retaining existing behavior. Subsequent edits are independent. Existing saved table/search preferences initialize the new view contexts when no new preferences exist. Record-document preferences are shared across records within the scenario; the selected record always restricts the document query.

CSV and ZIP export are not implemented. Their configuration switches remain off and disabled in every workspace. Saving through ConfigUI sets both export flags to false, including configurations imported with those flags enabled.

3.16. Configuration QA behavior

Creation and update forms follow the selected workspace’s detail field order, section headings, labels and read-only settings. In two-stage scenarios, record-scoped documents and the all-documents view retain their independent table, search, detail and permission settings. Disabling a shared attribute removes it from both document workspaces. Stored column preferences cannot restore fields that the current permissions hide.

A permission change also applies when a drawer or confirmation was already open: a revoked action cannot be submitted. Configuration administration alone does not grant business actions. Restoring historical versions, CSV/ZIP export, column-header filtering controls and document summary cards remain unavailable; record summary cards are supported.

3.17. Recycle-bin configuration (in development)

General Overview includes scenario-wide trash, trash-bin visibility and deletion-only-for-trashed settings. Search settings control whether each workspace offers Include trashed items in its table filter bar. The filter also requires the workspace’s Trash, View trashed items and Include trashed items in search permissions. Clearing it returns to active items only.

Recycle bin appears below Documents and above History in scenario navigation. Its Records and Documents entries open separate lists with their configured columns; the Documents list also includes trashed documents whose record is active. One-stage bins show Documents only. The breadcrumb returns to the scenario. Trashed items are read-only. Editors offer Move to recycle bin and permanent Delete only when the current state, permissions and deletion policy allow them. The record summary card uses a three-dot menu for the same state-sensitive Edit, Delete, Trash and Restore actions; Restore has a recovery icon. A narrow status column keeps trash markers aligned separately from business values. Permanent deletion from the bin requires typing the displayed item name, or DELETE for bulk operations and items without a display name. Record scenarios provide independent automatic/ask modes for trashing children, restoring children and restoring a document’s parent. Native repository cascades are identified as repository-managed and cannot be overridden. Existing disabled trash cascading preserves record-only behavior.

Confirmation shows affected counts and shared/global impact. When children are included in record restoration, all trashed children are restored, even those trashed earlier independently. Declining children applies the action to the record only; declining a required parent restoration cancels document restoration. Relationships are preserved. Each action still requires its scenario permissions. Bulk operations replace the journal; partial failures refresh repository state and can be acted on again using fresh confirmation, without progress/recovery controls.

Note
 AFC-123 remains in development until replacement runtime, native-cascade and inheritance acceptance is complete. Database and configuration schema remain V2.

The ECR CoreTeam decision on reading retained content and annotations while trashed is pending, for both current and historical versions. Retention alone does not guarantee read access. The original delivered ECR 28.1.0 returns Not found for these reads while trashed; the same reads succeed after restoration. Do not promise preview or download access while trashed until the supported contract is decided and verified against an original delivered ECR artifact. For now, use the authorized Restore workflow and verify access after restoration, as described in Downloads, unavailable content and historical viewing; scenario settings cannot override this repository limitation.

3.19. Recycle Bin view configuration

Recycle Bin reuses the scenario’s existing view settings. Trashed records use the Records configuration. Trashed documents use the standalone Documents configuration, including in a Record scenario; they do not use Documents within a record. Changes to those views also apply in Recycle Bin. The configuration editor explains this inheritance beside the relevant settings. Recycle Bin retains separate permissions, trash-only searches and saved view preferences. There are no separate view configuration fields for trashed items.
